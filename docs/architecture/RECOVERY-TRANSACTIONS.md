# Recovery transactions

## Backup storage contract

`archrescue-backup::transaction` complements the original one-shot backup API. The guided interface and the `backup-start`, `backup-list`, `backup-resume` and `backup-verify` commands use the transaction API. An operation owns a newly created directory named `archrescue-backup-<operation ID>` under the verified independent destination.

- `manifest.json` is an immutable schema 1 plan containing selected relative paths, directory topology, exact file sizes, source SHA-256 values, creation time, initial runtime storage identities and stable recovery locations. The plan fingerprint also binds the operation ID to these fields.
- `status.json` records the latest phase and terminal error when that phase can be persisted. A recorded Running phase can outlive its process. The operation must be rediscovered and revalidated after restart.
- `journal/<index>.json` binds a per-file state, acknowledged byte count and optional error to the plan fingerprint. Initial copies check cancellation while hashing and writing. A copying checkpoint is updated at 16 MiB intervals. A recovered count describes acknowledgements before interruption and can lag the actual staging length.
- `journal/<index>.part` holds an incomplete file. Resume starts that file at byte zero after validating and removing its owned staging entry. Payload publication uses a same-filesystem rename that fails if the final pathname exists.
- `payload/` contains published data. An interrupted copy retains a valid checkpoint independently of a report export. A report records planned, acknowledged, verified and reused results, with a checkpoint and hash per file.

Checkpoint snapshots contain a SHA-256 digest over the JSON data. The writer creates a new temporary record, flushes it and publishes it by rename. Linux requests directory sync and uses `renameat2` for exclusive publication. Windows uses `MoveFileExW` with write-through requested and flushes the opened data file before publishing it. The sequence reduces exposure to torn updates under ordinary process termination. Filesystem, device-cache and abrupt power-loss guarantees vary. A missing or corrupt authoritative record, invalid checksum, incompatible operation or unknown payload path fails validation. A temporary record from an interrupted update never establishes completion. [Microsoft MoveFileExW contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

Before copying, resume verifies current physical separation on Windows, matches the on-disk table and partition identity, extent geometry, filesystem serial and directory within the volume, and rescans the source selection. It hashes source content and every retained output, checks capacity for remaining work and rejects conflicting paths. It rereads staged content before publishing, then verifies the complete published selection before recording completion. If publication completed before the last checkpoint, a matching prepared record, absent staging entry and full hash verification allow recovery without overwriting a file. An exclusive per-operation lock prevents two cooperative writers. The offline, quiescent-media assumption still applies. The checksums detect corruption and bind records to a plan. They provide no authentication against a party who can rewrite the entire destination and recompute its hashes.

The Linux adapter verifies separate filesystems and uses device and directory inode identity. Linux acceptance exercises process restart. The reboot workflow is validated on the Windows identity path. The portable path rules reject links, reparse points, traversal, case collisions, alternate-stream syntax and unsupported filenames. File data and empty directories are preserved. ACLs, timestamps, sparse allocation and alternate streams are outside this schema.

## Diagnostic and repair boundaries

The existing report schema accepts additive diagnosis and transaction fields. A structured finding records its stable ID, affected path, confidence, evidence, proposed next action and whether it blocks repair. Offline PE file evidence identifies architecture and any readable kernel version resource. Windows installation edition and service state remain unresolved. Same-disk GPT topology yields a candidate association. The BCD must still resolve the loader and target. BCDEdit receives a temporary copy only after independent scratch storage is proved.

A schema 1 repair plan records the installation, ESP, disk and volume identities, exact command arguments, independent backup references, scratch estimate, blockers and external rollback procedure. The Windows lab command re-derives the plan before execution and compares its hash, target and arguments with the authorized plan. It requires the build-registered GPT disk and partition IDs, an explicit plan token, an isolated UEFI WinPE session, separate verified preservation and a filesystem dirty-state check. The command uses BCDBoot with an explicit ESP drive and `/f UEFI`. Microsoft documents that supplying `/s` avoids adding a firmware NVRAM boot entry. [Microsoft BCDBoot options](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/bcdboot-command-line-options-techref-di)

The repair attempt records the output, exit code, independent backup recheck and post-repair observations. Bootability requires an actual guest restart and external observation. Restore the disposable overlay or external snapshot for rollback. The technician view previews repair and exposes the conditions. Actual repair is available only through the lab entry point.
